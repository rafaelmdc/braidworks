# Listing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A list result carries its own size and completeness (`Listing`), stated once by a backend and shown the same way everywhere. That replaces `.count` siblings, the `.total` row column, display caps inside weavers, and the count fields in `coverage`.

**Architecture:** `Strand` gains `total`/`complete`. The shared mapper unpacks a backend's `Listing` into them and defaults set-output lists to complete. `Result` turns any strand that carries them back into a `Listing`, and one formatter renders it. Declared `.count` types become aliases that the mapper derives from the list's total. Then each weaver drops its display slicing and coverage counts and returns a `Listing` where retrieval is partial.

**Tech Stack:** Python 3.12, `uv` workspace, pytest, ruff.

**Spec:** `docs/superpowers/specs/2026-11-05-listing-design.md`

## Global Constraints

- `Listing` is a `list` subclass. Slicing/copying returns a plain `list`. Attributes `total: int | None`, `complete: bool`, both read-only.
- `complete is True ⇒ total == len`. `total`, when set, is `≥ len`. `Listing(...)` raises `ValueError` otherwise.
- `Strand.to_json()` writes `total` / `complete` **only** when not the defaults (`total is None`, `complete is True`), so old JSON round-trips byte-identically.
- One formatter, `braidworks.core.listing.describe_size(value) -> str | None`, renders `"25 of 321"` / `"25+"` / `"321"`. Every presenter uses it.
- `.count` aliases: kept for one release. The mapper derives them from the list's `total`, and they're omitted when the total is unknown. Removal is tracked for before #331, with no new `verify` warning in this release (designer's call: every current spec legitimately declares them).
- Counts of other things keep #351 names (`*.experiment_count`, `*.association_count`).
- Core version: minor bump `braidworks-core` (new public API). Weavers that adopt it raise their floor to that version and bump all three version sites (spec, `pyproject.toml`, `vocab.py` via regeneration; `ncbi_weaver` by hand).
- No cache schema bump: the cache key includes `weaver_version`, and every weaver that capped a list gets a version bump in Part B. Old entries for unbumped weavers hold uncapped lists, which the default (complete) describes correctly.
- Never weaken conformance/contract tests. Tests that asserted capped lengths or coverage count fields are *updated to the new truth*, not deleted.

## Review Focus

1. **A backend caps but forgets to say so.** The golden/live total assertions (Task 5) must catch it. Expected: verify fails with the expected vs got total.
2. **An empty list with a known total of 0.** `Listing([], total=0)` is complete and displays `"0"`. `Listing([], total=None, complete=False)` displays `"0+"`.
3. **A fan-out child.** Its scalar member must not show the parent's `total`. Expected: a child row's value is a plain scalar and the parent row keeps the `Listing` (Task 3 test).
4. **CSV/pandas export of a `Listing`.** The cell is the list as today, plus a `<type>.total` column. A row with no value has an empty total cell (Task 4 test).
5. **A JSON round-trip of a strand set holding a partial list** (cache, run store, resume). `total`/`complete` survive and `resume()` rows still show `"25 of 321"` (Task 2 test).

### Task 2: `Strand.total/complete`, mapper unpacking, derived `.count` aliases

**Files:**
- Modify: `braidworks-core/src/braidworks/core/strand.py` (`Strand`), `braidworks-core/src/braidworks/core/mapper.py` (`map_lookup`, `map_resolver`, `_candidate_result`), `braidworks-core/src/braidworks/core/capability.py` (docstring of `totals`: "deprecated alias; the count is derived from the list's total")
- Test: `braidworks-core/tests/test_listing_strands.py`

**Interfaces:**
- Consumes: `Listing` (Task 1).
- Produces: `Strand(type_id, value, ..., total: int | None = None, complete: bool = True)`. `Strand.as_value() -> Any` returns `Listing(value, total=…, complete=…)` when `total is not None or not complete`, otherwise `value`. Mapper rule: a `Listing` value becomes `Strand(value=list(v), total=v.total, complete=v.complete)`. A plain list under a `capability.set_outputs` type becomes `total=len(value)`, complete. For each `(list_type, count_type)` in `capability.totals`: if `count_type` is in `allowed`, the record didn't set it, and the list strand has `total is not None`, emit `Strand(count_type, total)`.

### Task 6: Per-weaver migration (repeat for each weaver below)

The recipe, per weaver:
1. Remove every display slice (`[:10]`, `[: self._limit]`, `[:_CHILDREN_LIMIT]`, `display_limit`) on values the backend returns. Keep any cap that bounds **retrieval** (page/request limits, `max_partners`), and where it can cut the result, return a `Listing` with the known `total`, or `total=None, complete=False`.
2. Stop writing `.count` values that are a declared list's total (the mapper derives them). Keep the spec's `totals` and `produces` entries (aliases).
3. Remove count fields from `…coverage` dicts: `observed_*`, `displayed_*`, `display_limit`, `display_count`, `total_partners`, `complete`, `source_complete`, `count_scope`, `fan_scope`. Keep source context. If a coverage dict becomes empty, drop that output from the spec (regenerate vocab per `weaverkit/docs/safe-regeneration.md`).
4. Update that weaver's tests that asserted capped lengths or the removed coverage fields to the new truth. Add a golden `"<list>.total" = N` to the spec for its main list capability.
5. Bump the version in all three sites, raise the floor to the new `braidworks-core`, and update the CHANGELOG/README note if the weaver keeps one.
6. Run `make verify-weaver SPEC=weavers/<w>/weaver.spec.toml PACKAGE=<w>` and `make -C weavers/<w> test`. For API backends also run `BRAIDWORKS_RUN_LIVE=1 make -C weavers/<w> test-live`.
