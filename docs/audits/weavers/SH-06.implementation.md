## Implementation boundaries

NCBI and BacDive compose the existing domain-neutral `map_bounded` helper; no new
scheduler, repository layer or hierarchy was added. Each lookup chain retains its
source-local parser, pagination and status policy. Duplicate work is shared only
within the current batch/build, with no persistent cache or resume implementation.

The existing `PacedHTTPClient` gains an optional positive finite `default_rate`.
Its existing request hook also paces redirects/authentication round trips. An
explicit executor budget or environment rate takes precedence. Defaults remain
unset for all other users of this client. NCBI uses 5 requests/second, following
[the official Datasets limit](https://www.ncbi.nlm.nih.gov/datasets/docs/v2/api/api-keys/).
BacDive uses a conservative project default of 2 requests/second, not a claimed
provider quota. These local budgets are shared per weaver/backend inside a process,
not across independent processes or applications sharing an IP address.

GMrepo's frozen `AcquisitionPolicy` round-trips through JSON. Its synchronous client
is source-local because acquisition already uses urllib and worker threads. A
thread-safe admission gate spans both acquisition stages. All retries are counted
against the same call budget. Only transport/time-out errors and HTTP
429/500/502/503/504 retry; decoding/schema errors, other statuses and programming
faults do not. Backoff and supported Retry-After delays share the gate. A provider
Retry-After beyond the configured waiting budget fails rather than retrying early.

The worker helper queues at most the configured number of jobs. Unexpected faults
stop further submission and cancel queued work; already-running synchronous HTTP
attempts finish or hit their existing 180-second timeout. Summary taxa, phenotype
inputs and run profiles shared across phenotype stages reuse source work.

Required catalog failures abort staging and preserve an existing target. Individual
summary/profile failures, including call-budget exhaustion, retain explicit
incomplete coverage in the manifest. Existing schema 2 databases remain readable.
Summary/profile resource separation means distinct acquisition stages and coverage
sections; storage remains one SQLite database with one atomic complete replacement.

## Configuration and migration

- NCBI: `DatasetsV2Backend(max_concurrency=4)`;
  `build_ncbi_weaver(..., api_max_concurrency=4)` exposes the same positive integer
  limit. Existing `max_report_pages` separately bounds each pagination traversal.
- BacDive: backend and both public builders accept `max_concurrency=4` alongside
  `max_strains_scanned`. Full scientific-name inputs are the reuse key.
- Both runtime sources: explicit `BRAIDWORKS_RATE_LIMITS=<weaver>:api=<rate>` or
  an executor request budget overrides default pacing. Concurrency is not rate.
- GMrepo: `ensure_gmrepo_db(..., acquisition_policy=AcquisitionPolicy(...))` and
  the configured builder accept the policy. Defaults: 4 workers, 2 requests/second,
  3 attempts, 10,000 total calls, 1-second exponential backoff, maximum retry delay
  60 seconds. These are project defaults, not a documented GMrepo quota.
- GMrepo's `meta.acquisition.requests` records policy, actual calls/retries and
  budget exhaustion. Refresh an existing database to obtain this metadata.
  Adding profiles still requires a full `refresh=True` rebuild.
- No capability/output-key changes or consumer schema migrations are required.
  Lower default acquisition concurrency and mandatory default source pacing can
  increase wall-clock time; callers can explicitly configure the policy.
- Versions: core 0.21.2; NCBI 0.2.8; BacDive 0.1.9; GMrepo 0.2.4. NCBI/BacDive
  require core >=0.21.2 for source defaults. All three weaver version sites agree.
